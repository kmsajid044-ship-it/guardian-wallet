# Security self-assessment

Scope: the Guardian Wallet research prototype as committed, running on the local FISCO BCOS network (a permissioned chain operated by the team) with USD and CNY demo balances and no real money. The threat model is in [THREAT_MODEL.md](THREAT_MODEL.md). Numbers below come from [EVAL_REPORT.md](EVAL_REPORT.md), [EXECUTION_EVIDENCE.md](EXECUTION_EVIDENCE.md), and the test suites; transaction hashes are from `evidence/evidence.json` (blocks 3241–3358).

## Known risks

| Risk | Impact | Mitigation in this prototype | Residual risk |
|---|---|---|---|
| **Owner key compromise** | The owner can change policy, roles, and recipients, approve pending items, withdraw savings, and resume. A stolen owner key controls the wallet. | Out of the agent-compromise threat model. Keys are test-only, generated locally into the git-ignored `.env`; owner actions are separate from agent actions and audited; a production web build refuses to embed a demo owner key and requires an injected browser wallet. A production design would use multi-party or hardware-backed owner signing and a time delay on policy changes. | High impact. Not mitigated in-contract: there is no owner multisig or timelock. |
| **Demo owner key is a publicly known local test key** | The local `.env` used to produce the published evidence signs as owner `0xf39Fd6e51aad88F6F4ce6aB8827279cffFb92266` and agent `0x70997970C51812dc3A010C7d01b50e0d17dc79C8`, which are the default Anvil/Hardhat development accounts #0 and #1; their private keys are published in Foundry and Hardhat documentation (the owner key also appears in vendored `contracts/lib/forge-std/test/StdCheats.t.sol`). Anyone who can reach that chain can act as owner or agent. | Acceptable only for a local permissioned demo with demo units: the nodes listen on loopback, no real money exists, and no project file contains the key values (git history scan). `pnpm run setup` generates fresh random identities into a new git-ignored `.env` instead of reusing these. Production would hold owner and agent keys in an HSM or a hardware wallet, never in a file. | Low for the local demo; unacceptable for any shared or production deployment. |
| **Guardian collusion** | The guardian can only pause. A colluding or compromised guardian can stop payments (availability) but cannot resume, move value, or change configuration; owner plus guardian collusion adds nothing beyond the owner's own power. | Guardian surface is `pause()` only (`GuardianWallet.sol:162`); resume is `onlyOwner`; the owner can replace the guardian (`setGuardian`); invariant I6 probes guardian resume. In the demo deployment the guardian is the zero address (disabled). | Low: denial of service by pausing until the owner resumes or rotates the guardian. |
| **LLM misunderstanding** | A model can pick the wrong contact or amount. Within T1 limits, a wrong proposal executes autonomously. | The model sees contact IDs only and must return a strict schema; missing fields produce a targeted question, never a guess (eval 9/9); firewall, pre-check, simulation, and risk scoring run on every proposal; the contract bounds any single autonomous payment below 200 USD and the day to 1,000 USD, to allowlisted recipients only. | Medium: a misread request under 200 USD to an allowlisted contact executes. The evaluation used the deterministic parser, so model misunderstanding rates were **not** measured; `pnpm eval --llm=configured` runs the same scenarios through a provider. |
| **Untrusted content could trigger T1 payments** (found and fixed during this assessment) | Before the fix, an untrusted message without injection phrases, such as an invoice saying `Pay ana 190 USD`, scored 30 (`UNTRUSTED_SOURCE` 20 + `FIRST_PAYMENT` 10) and executed at T1 (verified on FISCO BCOS: route `EXECUTED`, tier T1, transaction `0x20eda84f…faaf2e`). | Fixed: the tier gate routes every payment, savings, or recurring request with an untrusted intake source to T2 (`agent/src/policy/tierGate.ts`, `agent/src/pipeline/pipeline.ts`). Below the approval threshold it is held with `UNTRUSTED_SOURCE_REQUIRES_APPROVAL` and nothing is signed; at or above it the contract pending item waits for the owner. Untrusted recurring requests no longer create schedules, and plans keep their intake source. Tests: `api.e2e.test.ts` "holds every untrusted payment or savings request for T2 owner approval and moves nothing before approval", `tierGate.test.ts`, `planner.test.ts`; eval X09 on FISCO BCOS. Allowlist, limits, and the firewall still apply. | Low: an owner can still approve an untrusted request they misjudge. A sub-threshold held request has no on-chain pending item; the owner re-issues it as a trusted request to proceed. |
| **Local owner endpoints hold the owner key** (demo only) | For the local demo, the agent service signs owner actions (`/owner/pending/:id/approve`, `/owner/pause`, `/owner/unpause`, `/owner/policy`, `/owner/recipients/:id`) with the owner key from `.env`. A process running as the same OS user can read `.env`, and therefore also the per-run owner session file. | Every `/owner/*` route requires the per-run owner session token in `x-owner-session` (32 random bytes, generated at agent start, compared in constant time, never logged; `agent/src/api/ownerSession.ts`). Requests with a non-loopback `Host` or a foreign `Origin` are refused before the body is parsed. The token reaches only the local owner console, through a same-origin, loopback-host Vite dev route (`web/owner-session.ts`); the file is mode 0600 under git-ignored `.demo/`. The API binds to `127.0.0.1` only. | Low for the local demo: other OS users, cross-site pages, and DNS-rebound pages are refused; same-user processes were already trusted with `.env`. The production design removes the owner key from the service and signs owner actions in the injected browser wallet. |
| **Permissioned-chain trust assumptions** | The team operates all four FISCO BCOS nodes. PBFT tolerates one faulty node of four, but a single operator controls all of them and could rewrite or withhold history; the local chain runs with `is_auth_check=false`, and execution balances are bootstrapped by the owner through the console. | Every exported hash is re-fetched from all four nodes with byte-identical receipts (118/118 each); a node data snapshot with its SHA-256 is published; `verify-evidence --fresh` lets anyone build their own network and reproduce all effects (16/16 scenarios, 118/118 transactions), so the results do not depend on trusting our nodes. | Medium: the original hashes are only as trustworthy as the team operating the nodes; reproducibility, not the hashes, is the independent check. |
| **FX snapshot staleness** | The USD/CNY rate is a fixed, illustrative snapshot (`7.10`, `asOf 2026-10-16T00:00:00Z`, `risk-intel/src/server.ts`), not a market rate, and the owner console shows it as a static label. It does not change and has no maximum-age check. | Labelled as an illustrative, cached, read-only snapshot with its date, and the service returns a note saying it is not a market rate; no amount is computed from FX (`quoteFx` is not called by any payment path); payments are entered and enforced per currency. | Low: an owner could misjudge the value of a payment from an outdated reference. |
| **CNY-denominated demo units may raise regulatory questions in Mainland China** | Balances denominated in CNY on a blockchain, even a local permissioned one, could be read as issuing or circulating a CNY-linked instrument, which Mainland China regulates closely. | No value: demo units are minted by the owner for illustration only and cannot be bought, sold, redeemed, or withdrawn. Team-operated local chain: four loopback-only FISCO BCOS nodes, no external network. Research prototype: no users, no customer funds. No issuance: nothing is offered to anyone, and every place CNY balances appear (owner console, Value Dashboard, documentation, generated reports) carries exactly: "Simulated demo units denominated in CNY for illustration. No value, not issued, not redeemable, not a digital currency, not linked to e-CNY." The currency set is configuration (`config/currencies.json`), so a reviewer can run the demo with USD only. | Medium until reviewed: regulatory acceptance has not been confirmed with the organizers or counsel. |
| **Organizer acceptance of permissioned-chain hashes not yet confirmed** | If the organizers accept only hashes from a chain the team does not operate, the on-chain evidence may not count as submitted evidence. | Hashes, raw receipts, block hashes, and a node snapshot are published, and the fresh-network replay reproduces every result. By the project's own rules, no external chain is used. | Open: awaiting organizer confirmation. |
| **Local FISCO BCOS consensus stall** (operational) | Twice in development, after the network sat idle for a long time, the nodes stayed connected but stopped committing blocks; agent requests waited on a receipt. | `./scripts/chain-down.sh && ./scripts/chain-up.sh` restored progress with ledger data intact (evidence verification passed afterwards). The node snapshot procedure was ruled out as the cause: restarting a node and committing immediately afterwards succeeded. | Low for a demo: availability only. The root cause was not determined. |
| **Owner-approved payments are not capped by the daily limit** (by design) | `approve` counts the payment toward the day's spending but does not enforce `dailyLimit`, so the owner can exceed it. | Intended: I1 bounds autonomous outflow; above the line the human decides. Approved spending still consumes the day's autonomous allowance. | Accepted. |
| **Plans and recurring jobs are held in memory** | Restarting the agent service drops draft plans and recurring schedules. | Each occurrence re-enters the full pipeline, so nothing executes without the usual checks; transitions are audited. | Low: availability only. |

## Fixed during this assessment

- The local owner endpoints were unauthenticated, so any local process, another OS user, or a browser page reaching `127.0.0.1` could approve, pause, or change policy. They now require a per-run owner session token, refuse foreign origins and rebound host names, and are covered by `agent/src/exec/api.e2e.test.ts` (no token, wrong token, cross-site form post, foreign `Origin`, rebound `Host` all refused with nothing signed) and `web/owner-session.test.ts`.
- The I5 invariant asserted `savings ≥ 0` on an unsigned value, which can never fail. It now checks that no account other than the wallet holds savings in either currency and that wallet savings never fall below the total deposited; a deliberate over-count in the handler makes it fail.
- The owner console's FX tile disagreed with the service snapshot; it now shows the snapshot rate and date, and states that no amount is computed from it.
